# Technical research

Target: Anki Desktop 26.09 (tag e62e773), the current stable release checked 2026-11-03. No Anki Desktop installation was found in the usual Windows install locations or on PATH. The test environment uses the 26.9 Python packages, not Anki's bundled Python/Qt runtime. Other releases are deliberately disabled.

Sources: [Anki source](https://github.com/ankitects/anki/tree/26.09), [add-on hooks](https://addon-docs.ankiweb.net/hooks-and-filters.html), [configuration](https://addon-docs.ankiweb.net/addon-config.html), [background operations](https://addon-docs.ankiweb.net/background-ops.html), [searching](https://docs.ankiweb.net/searching.html), [statistics](https://docs.ankiweb.net/stats.html), and [sharing add-ons](https://docs.ankiweb.net/addons/sharing). See the official package guidance for ZIP layout.

`qt/aqt/deckbrowser.py` invokes `deck_browser_will_show_options_menu(menu, did)` and `deck_browser_will_render_content(browser, content)`; the latter supplies already-rendered HTML, not a supported tree filter. The add-on appends CSS selectors for exact verified deck row IDs before the page renders, without replacing or parsing generated HTML. On inconsistent metadata it leaves the archive visible. The CSS relies on the current row structure and needs desktop compatibility testing. A simple link is appended using the supported hook and `webview_did_receive_js_message`. Native Qt widgets inherit Anki's palette; no global theme CSS, fonts, or images are used. `aqt/theme.py`, `aqt/webview.py` and the 26.09 hook definitions were inspected. Theme switching is not verified here.

`anki.decks.DeckManager.rename` delegates to the backend, renames children, and preserves deck identity. `anki.decks.card_count` includes original deck IDs for filtered cards; the add-on refuses a move when those cards are currently in a filtered deck. Renaming may change inherited parent limits and due-count aggregation, even though individual deck configurations remain attached. The archive container has normal deck settings. FSRS scheduling is not intentionally changed; tests must not be confused with a guarantee about future reviews.

`Collection.get_config` and `set_config` store JSON in collection config. The source says this config is sent on every sync and should be small. It is shared collection state, not local add-on configuration. Concurrent edits on separate devices can conflict and config and deck changes may sync at different times; perform one archive or restore on one device, sync, then sync the other device before further changes. There is no tested conflict resolution. Each item is keyed by deck ID. An intent record is written before moving a deck and is retained if a move cannot be verified. Missing, moved or unrecorded decks are surfaced and block filtered statistics; records are never automatically deleted. Undo entries combine configuration and deck changes where Anki supports it.

The stats page (`ts/routes/graphs/WithGraphData.svelte`) sends its search to the native `graphs` backend; `rslib/src/stats/graphs/mod.rs` searches cards and obtains review entries for those cards. Empty collection searches have special handling, including deleted-card history. Anki explicitly supports arbitrary searches in modern statistics. The add-on constructs its exclusion with `Collection.build_search_string` and `SearchNode`, using the current container name. The modern stats hook attaches to page load and fills the field `statisticsSearchText`, which Anki's `RangeBox.svelte` explicitly describes as an external API; it dispatches the focus, input and change events the component uses. The Svelte root disables SSR, so the field is produced by the client. A native notice warns if the field cannot be found. Anki 26.08.1 and 26.09 use the same RangeBox implementation. This integration is still version-sensitive and has not been verified end to end in the desktop application. The definition is current deck membership, not historical membership. Individual graph correctness and global figures have not been validated by desktop graph tests. Native whole-collection mode remains available. Third-party stats and mobile are unaffected.

`CollectionOp` and `QueryOp` are used for background collection work and native progress/refresh. Collection config writes and the rename are separate backend operations, not an atomic cross-operation transaction: intent records and explicit integrity warnings reduce but do not remove interrupted-operation and sync risks. Version-sensitive APIs, including deck metadata and stats behavior, need revalidation before broadening compatibility.
